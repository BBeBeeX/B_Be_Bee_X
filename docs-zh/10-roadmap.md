# 10 —— 路线图与风险

> **本篇回答什么。** 构建的先后顺序、每个阶段"完成"意味着什么，以及对可能出问题之处的如实盘点。

排序原则：**尽早证明风险最高的那条架构论断。**"同一张插件图无需修改即可同时运行在 Hermes 与 Electron 渲染进程中"——这个论断要么成立，要么项目需要重新设计；在第一周验证它代价很小，到第六个月才发现则是灾难。所以 M0 刻意朴实无华——在 M1 之前不会有任何音乐响起。

---

## 里程碑

### M0 —— 内核在两个平台上跑起来

构建 `@BBeBee/protocol`、`@BBeBee/kernel`，以及最小核心服务（`paths`、`fs`、`store`、`db`、`logger` 传输层）的双份实现。两个外壳都能启动、加载一个极简插件并渲染它贡献的视图。还有来自 [09 §6](./09-project-structure.md#6-testing-strategy) 的一致性测试 harness 与泄漏测试。

**完成标准**
- 同一个插件包在 iOS 模拟器、Android 模拟器与 Electron 上加载并激活，插件内不含任何条件分支代码。
- `pnpm test` 对所有实现跑绿 `fs`、`db` 与 `store` 的一致性测试套件，其中 Expo 侧的实现要在设备上运行。
- 禁用插件后，Context 快照被精确还原。
- 插件检查器展示 fiber 树，且各 effect 均带标注。

**为何排第一。** 在这一步通过之前，每个 ADR 都只是假设。如果 Cordis 在 Hermes 上表现异常、Metro 无法解析其 `exports` 映射、或标准装饰器无法转译——问题都会在这里暴露，而此时退出成本仍然很低。

---

### M1 —— 能播放音乐

`core-audio-webaudio`、`plugin-player`、`plugin-source-local`、`plugin-local-scanner`，外加两个外壳中足以浏览曲库、控制播放的 UI。媒体会话（media session）集成。

**完成标准**
- 扫描一个 ≥ 5,000 个文件的文件夹；对未变化的曲库做增量重扫，只消耗 stat 调用。
- 播放、暂停、进度跳转、上一曲、下一曲、队列重排——三个平台全部支持。
- iOS 与 Android 上锁屏与通知栏控件可用；桌面上为 MPRIS/SMTC/Now Playing。
- 移动端切后台、桌面端隐藏窗口后，播放不中断。
- 拔出耳机即暂停（[05 §5](./05-audio-playback.md#5-interruptions-focus-and-routes)）。
- 队列与播放位置在重启后恢复，且不自动开始播放。

---

### M2 —— 第二个音源

让提供方 SPI 真正落地：`plugin-source-subsonic`，具备多实例支持、认证、搜索、浏览与流解析。`ctx.sources` 聚合，以及身份关联表。

**完成标准**
- 同时配置两个 Navidrome 实例，cookie jar 相互隔离，认证状态各自独立 —— 一个实例设置的 cookie 绝不会被发给另一个。
- **登录一次，一直在线。** 强杀应用并重新启动：会话从持久化 jar 中恢复，无需任何提示，也不存任何密码（[06 §4.1](./06-music-sources.md#41-session-persistence--cookies-survive-the-app)）。
- **登出后不留痕迹。** `signOut()` 之后，jar 的持久化副本与 secrets 命名空间都不复存在；重新启动后该音源显示为未登录状态。
- 一个只实现必需核心的提供方（`plugin-source-http-url`）与其他提供方一同配置，没有任何界面因缺少可选方法而出错。
- `searchAll` 返回按提供方分组的结果；某个提供方失败时予以报告，而不让整个搜索失败。
- 会话中途令牌过期时透明刷新；刷新失败则就地显示重新登录，同时缓存内容仍可浏览。
- 完整的错误分类法均被覆盖——[06 §6](./06-music-sources.md#6-errors) 中每一行都有对应测试。
- 同一录音的本地曲目与服务器曲目通过 ISRC 关联，在曲库中显示为一条条目、两个音源。

**为何排第二。** 只有一个提供方证明不了 SPI 的任何东西。第二个提供方才是抽象要么得到验证、要么被揭穿为"第一份实现的描述"的地方。

---

### M3 —— 离线

`plugin-download`（含可续传的任务队列）、`media_bindings`、下载策略，以及 `player/before-resolve` 替换机制。

**完成标准**
- 下载中途杀死应用；重启后从 `bytes_done` 续传，若 `etag` 已变化则干净地重新开始，而不是拼接出损坏的字节。
- 禁用 `plugin-download` 后，同一曲目转为流式播放，且行为完全一致——即 [09 §6](./09-project-structure.md#6-testing-strategy) 中的那个测试。
- 策略在真实的 `ctx.device.network()` 状态变化下遵守 `wifi_only` 与 `charging_only`。
- 底层文件被删除时移除绑定，而不是拖到播放时才失败。
- 持续使用之下，缓存淘汰始终保持在各类配额之内。

---

### M4 —— 听感达标

`plugin-dsp` 与 [05 §3](./05-audio-playback.md#built-in-effects) 中的内置效果。两个外壳中各有效果链编辑器 UI。

**完成标准**
- EQ、normalize、compressor、reverb 各凭一份实现，即可在 iOS、Android 与桌面上运行。
- 每个效果的离线渲染测试都在容差内与参考值吻合。
- 拖动 EQ 滑块不重建音频图，也不产生爆音。
- 播放中启用或重排效果，除预期变化外听不出任何差别。
- 在低端 Android 设备上，`tempo-pitch` 会报告 dropout 并自行禁用，而不是拖垮整条效果链。

**为何排这么晚。** 它是最显眼的功能，却是架构风险最低的——M1 确立的 Web Audio 契约要么支持它、要么不支持，到 M4 时答案早已揭晓。

---

### M5 —— 桌面端第三方插件

`plugin-loader-dynamic`、`BBeBee-plugin://` 协议、安装/更新/卸载、能力授予与隔离（quarantine）。

**完成标准**
- 在仓库之外构建的插件可以从本地文件或 URL 安装，并在严格 CSP、`nodeIntegration` 关闭的情况下加载。
- 插件请求未被授予的能力时收到 `CapabilityError`，操作干净地失败，而不是让应用崩溃。
- 加载时连续抛错两次的插件被隔离；此后应用正常启动，并说明原因。
- 卸载时先销毁（dispose）fiber 再删除文件；"移除数据"恰好只删掉该插件带命名空间前缀的表。

---

### M5 之后

尚未排期，但架构已为其留好位置，且不被上述任何一项阻塞：

- **同步** —— 一个 `SyncProvider` SPI，附带基于文件/WebDAV 的参考实现。表结构中已备好 `device_id`、`revision` 与 `sync_state`。
- **真正的沙箱** —— 为第三方插件提供 `Worker` 或 QuickJS realm，并把 [03 §7](./03-plugin-system.md#7-capability-model) 的能力语法用作桥接协议。
- **移动端运行时插件** —— 沙箱落地后即解除阻塞。
- **指纹匹配** —— 一个为 `track_links` 供数的 AcoustID 插件。
- **更多提供方** —— Jellyfin、播客源，以及 SPI 最终证明能容纳的一切。

## 风险登记册

按预期代价而非发生概率排序。

### 🔴 Cordis 尚处于 release candidate（RC）阶段

它的 README 写明 API 可能不作通知就变更，而它又是一切的地基。

*缓解措施* —— 精确锁定版本；刻意收窄的 API 表面；插件从 `@BBeBee/kernel` 而非 `cordis` 导入，让签名变更由一个适配层吸收；以及语义测试，在升级时立即大声失败（[09 §5.1](./09-project-structure.md#51-the-cordis-rc-problem)）。

*触发重新评估的条件* —— 如果一次 RC 版本升级破坏了设计所依赖的隔离或 effect 语义，备选方案是把锁定的版本 vendor 进仓库。Cordis 核心只有几千行、两个依赖，这让该方案切实可行，而非纸上谈兵。

### 🔴 `react-native-audio-api` 尚未到 1.0

ADR-4 把整套跨平台 DSP 方案押在了一个 `0.13.x` 的包上。

*缓解措施* —— 契约是**标准 Web Audio API**，而非该库自身的形态，因此切换成本有上限。文档化的备选方案是改用基于 `react-native-track-player` 的 `core-audio-rntp`，代价是放弃移动端 DSP。

*早期预警* —— M1 会实测流式播放、无缝播放与锁屏控件。如果它在此令人失望，还能赶在 M4 依赖它之前重新审视这个决策。

### 🟠 抽象泄漏的速度快过修补的速度

`ctx.fs` 的两份实现渐生漂移；某个功能插件悄悄开始依赖桌面端行为；六个月后，"在我机器上能跑"的含义就变成了"在桌面端能跑"。

*缓解措施* —— 一致性测试套件是第一道防线，必须在 CI 中于真实设备上运行，而不能只在 Node 里跑。ESLint 导入禁令（[09 §3](./09-project-structure.md#3-dependency-rules)）能拦下最粗糙的泄漏。已知泄漏点用 ⚠️ 记录在案而非藏起来，让贡献者在自己的代码出事之前先撞见它们。

### 🟠 双份 UI 复制的不只是视图层

ADR-2 接受了视图要写两遍。失败模式是逻辑悄悄渗进视图——从此逻辑也要写两遍，而两个外壳开始出现*行为*上的分歧。

*缓解措施* —— 三包约定，钩子放在 headless 包里（[08 §4](./08-ui-architecture.md#4-binding-services-to-react)），加上 CI 中的组件对等（parity）测试。一旦桌面端与移动端对某个按钮的行为出现分歧，按定义这就是 headless 包的 bug。

### 🟠 iOS 后台限制

非音频类的后台工作在设计上就不可靠，任何架构都改变不了这一点。

*缓解措施* —— 约束被写进契约：提供 `ctx.background.canRunInBackground()` 让插件主动询问；`download_tasks` 按分块记录检查点，让中断的代价很小。UI 对"什么会继续、什么不会"如实相告，而不是摆出一条悄然卡死的进度条。

### 🟡 第三方插件尚未被真正约束

运行时加载的插件与渲染进程共享同一个 realm。能力模型是纵深防御，不是沙箱，[03 §7](./03-plugin-system.md#what-this-is-not) 对此直言不讳。

*在真正的沙箱出现之前的缓解措施* —— 安装时的能力授权弹窗，写明究竟授予了什么；完整性哈希；反复失败后进入隔离；以及一个不粉饰现状的安装警告。设计并不依赖"围堵问题已被解决"这一前提；日后补上沙箱时，改动的是桥接层，而非插件契约。

### 🟡 两个大型框架之间的版本漂移

Expo SDK 升级会一并带动 React Native 与 React；Electron 升级会一并带动 Node 与 V8。二者不会自发地在 React 版本上保持对齐。

*缓解措施* —— React 与 React Native 锁定在 Expo SDK 57 所规定的版本上，桌面端渲染进程跟随 Expo 使用的 React，而非最新发布版（[09 §5](./09-project-structure.md#5-version-matrix)）。升级是一项排期任务，以一致性测试套件作为闸门。选择 `node:sqlite` 而放弃 `better-sqlite3`，已经消除了最沉重的一项经常性成本。

### 🟡 SQLite 作为唯一存储

一个数据库承载曲库、播放列表、历史、下载、设置与插件表。当曲库庞大、扫描器高效激进、下载队列繁忙时，写冲突完全可能发生。

*缓解措施* —— WAL、扫描器内的批量写入，以及两个平台上统一的单一串行写入路径。如果真的成为问题，把易变表（`play_history`、`cache_entries`、`download_tasks`）拆分到第二个数据库文件是一项影响可控的改动，因为没有任何查询跨这些边界做 JOIN。

## 什么会证明这个设计是错的

值得提前写下，以便日后一眼认出：

- **如果最终只有一个音源落地**，提供方 SPI 就是纯粹的负担，直接实现反而更好。M2 就是检验。
- **如果插件从未在运行时被加载**，ADR-1 的桌面加载器、能力模型与清单就都是没有回报的成本，处处静态打包才是正确选择。
- **如果移动端与桌面端最终拥有实质不同的功能集**，双份 UI 就已经变成了两份*产品*，而 ADR-2 否决的 universal RN-Web 方案才是正确选择。

目前这三点都没有迹象。到 M5 时，三条全部可以检验。
