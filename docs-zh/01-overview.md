# 01 —— 总览与决策

> **本文回答什么。** BBeBee 是什么、刻意*不是*什么、面向哪些平台，以及其余一切所依赖的四个架构决策。如果写代码前只读一份文档，请读本文与 [02](./02-architecture.md)。

---

## 1. 我们在构建什么

一款用同一份代码库同时运行在桌面端与移动端的音乐播放器：播放器本身保持精简，几乎所有行为都以插件形式提供。

用户可见的产品很普通：曲库、队列、带均衡器的播放、离线下载、播放列表、歌词，以及从不止一处获取音乐的能力——磁盘上的一个文件夹、一台自托管服务器、一个流媒体服务。不寻常的是底下的形态：不存在一个拥有这些功能的特权"核心"。曲库是一个插件。下载器是一个插件。下载器所使用的文件系统访问同样是一个插件。

### 为什么这样构建

三条理由，按重要性排序：

1. **跨平台而不写条件分支。** 服务抽象的替代方案是让 `Platform.OS === 'ios' ? … : …` 散落在代码库各处，这会迅速腐化。在这里，平台差异只表达一次——以*加载了哪个插件*的形式——此后不再出现。
2. **音源天然是多元且不稳定的。** 每个流媒体后端都有不同的 API、不同的认证、不同的分页方式，以及不同的寿命。音源必须做到可在不触碰播放器的前提下增删。这迫使系统提供一个真正的 SPI（[06](./06-music-sources.md)），而不是一个碰巧只有一份实现的内部接口。
3. **生命周期正确性很难，而 Cordis 已经解决了它。** 注册事件监听器、打开套接字、持有音频节点、启动定时器的插件，在停用时必须把这些全部拆除。Cordis 的 fiber/effect 模型从构造上保证卸载是彻底的——这恰恰是大多数插件系统做错的部分。

### 目标

- 一张插件图，在 iOS、Android 与桌面端上无需修改即可运行。
- 插件可在运行时停用且不留痕迹——没有监听器、没有定时器、没有套接字。
- 新增一个音源只需改动一个新包。
- 音频路径在*所有*目标平台上都支持真正的 DSP 链（参数均衡 EQ、动态处理、卷积），而不只是桌面端。
- 离线优先：没有网络时，曲库与队列依然可用，应用依然可以导航。

### 非目标

在此明确写出，因为其中任何一条若被重新引入，都会改变架构。

- **不是 DRM 客户端。** 不集成 Widevine/FairPlay。需要 DRM 的音源超出范围；`StreamHandle` 类型预留了一个 `drm` 字段，门没有焊死，但没有任何实现。
- **不是服务器。** 不构建同步后端。跨设备同步被设计为一个 SPI（附带文件/WebDAV 参考实现），推迟到 M5 之后。
- **不抓取专有服务。** 提供方 SPI 的设计*支持*商业后端，第三方也可以编写此类插件，但本仓库随附的插件只面向开放协议：本地文件系统、Subsonic/Navidrome、Jellyfin，以及纯 HTTP URL。这既是范围决策，也是法律决策——开放协议拥有稳定的规范，参考实现可以据此构建。
- **不是通用扩展宿主。** 桌面端运行时加载的插件与应用处于同一个 JS realm。文档如实将其描述为*纵深防御，而非沙箱*（[03 §7](./03-plugin-system.md#7-capability-model)）。
- **范围内不做 Web 构建。** React Native Web 在技术上可行，但下文的决策 **ADR-2** 为桌面端选择了独立的 DOM UI，而浏览器目标会成为第三个外壳且没有离线方案。日后可重新审视；当前没有计划。

## 2. 目标平台

| 目标 | 宿主 | JS 运行时 | 内核所在 | UI |
|---|---|---|---|---|
| iOS | Expo / React Native | Hermes | 应用的唯一 JS 上下文 | React Native |
| Android | Expo / React Native | Hermes | 应用的唯一 JS 上下文 | React Native |
| 桌面端（macOS / Windows / Linux） | Electron | V8，渲染进程 | **渲染进程** | React DOM |

移动端需要**自定义开发构建**（`expo-dev-client`），而非 Expo Go，因为 `react-native-audio-api` 和若干核心服务模块包含原生代码。开篇即说明这一点，是因为它影响每一位贡献者的上手指引。

## 3. 架构决策（ADR）

这四项在设计写就之前即已敲定。每一项都记录了选择了什么、否决了什么，以及代价是什么。

### ADR-1 —— 插件在移动端静态打包，在桌面端可运行时加载

**决策。** 一份插件清单格式同时服务两个目标平台，由两个不同的加载器插件解析。在移动端，一个代码生成步骤为工作区中的每个插件发出静态 `import` 语句；配置只负责启用、停用与配置它们。在桌面端，插件还可以被安装到用户目录，并在运行时通过动态 `import()` 加载。

**已否决——处处静态打包。** 最简单，也曾是推荐方案，但它使桌面用户必须依赖项目发版才能获得任何第三方音源插件。对一个整体价值主张就是可插拔音源的应用而言，在唯一真正允许运行时加载的平台上，这是错误的取舍。

**已否决——双端运行时插件市场。** 在 iOS 上，下载并执行新 JavaScript 需要附带一个解释器沙箱才能符合应用商店合规要求。那是一个庞大的子系统——沙箱、能力授予、签名、版本管理——而且日后可以在同一份清单格式之后加入，不会使此处设计的任何内容失效。

**代价。** 需要维护两份加载器实现；一套仅桌面端拥有的安装/更新/隔离流程；一套能力授予 UI。移动端与桌面端可用的插件集合可能漂移，因此当贡献的视图缺席时，UI 必须能够降级。桌面端必须在不削弱自身 CSP 的前提下加载第三方代码——通过自定义协议解决，见 [03 §6](./03-plugin-system.md#6-loading-two-modes)。

### ADR-2 —— UI 拆分：移动端 React Native，桌面端 React DOM

**决策。** 两个外壳、两套组件库、一个无头核心。插件贡献与渲染器无关的**描述符**（descriptor：一条路由、一个槽位填充、一条命令、一个设置页），并在独立的包中为各目标平台随附视图实现。

**已否决——通用 React Native Web。** 只有一份 UI 代码库，Electron 渲染同一个 bundle，成本大约省一半。否决的原因是：桌面音乐播放器理应具备的交互——可调整大小的多栏曲库、右键上下文菜单、拖拽重排队列、键盘导航、原生窗口边框、托盘迷你播放器——恰恰是 react-native-web 会做得别扭的那些东西。在视图层花两倍的钱，换来的是一个用起来像桌面应用的桌面应用。

**代价。** 每个带 UI 的插件最多变成三个包。两套必须保持同步的 design-token 流水线。两套导航系统。一个纪律问题：把逻辑写进视图现在*成为可能*，架构必须主动阻止它（[08 §4](./08-ui-architecture.md#4-binding-services-to-react)）。

### ADR-3 —— Electron 内核位于渲染进程；`main` 是一个薄的原生宿主

**决策。** Cordis `Context` 创建在渲染进程中。`main` 进程持有 Node 与操作系统，通过 `contextBridge` preload 暴露一个狭窄的、以能力划定范围的表面，并且**不含任何业务逻辑**。桌面端的核心服务插件只是这层 IPC 表面之上的薄客户端。

**已否决——拆分内核（服务在 main，UI 内核在渲染进程）。** 这能让下载与播放在窗口关闭后继续存活。否决的原因是它引入了一个序列化边界和一层远程服务代理，而移动端没有对应物，这意味着插件图会随平台而异——正是本架构要避免的东西。

**已否决——内核只在 main。** 与移动端的分歧最大；UI 插件将完全无法共享内核。

**后果。** 桌面端与移动端都恰好有一个 JS 运行时，承载恰好一个 context。功能插件无法分辨自己身处哪个平台。代价是桌面端的后台工作与渲染进程的生命周期绑定——用"关闭窗口到托盘"来缓解，而不是靠架构。见 [02 §4](./02-architecture.md#4-what-background-means)。

### ADR-4 —— `react-native-audio-api` 是所有目标平台上首要的播放与 DSP 引擎

**决策。** `ctx.audio` 服务契约就是 **Web Audio API**。在 iOS 与 Android 上由 `react-native-audio-api` 满足；在 Electron 渲染进程中，由同一个包的 web 实现（或浏览器原生 Web Audio——两者是同一接口）满足。

正是这一决策使 DSP 需求变得可控。没有它，"移动端音频效果"意味着把原生 DSP 写两遍。有了它，十段均衡器就是一条 `BiquadFilterNode` 级联，在三个平台上行为完全一致。

**已否决——移动端使用 `react-native-track-player`。** 它在后台队列、锁屏控制与蓝牙/车机集成方面久经考验。否决的原因是它不暴露音频图，这会让 EQ 与音效成为桌面端专属——等于放弃一个已声明的目标。

**已否决——`expo-audio`。** 最简单，且停留在托管工作流内，但既没有队列引擎，也没有 DSP 图。

**代价与缓解。** `react-native-audio-api` 目前处于 `0.13.x`——1.0 之前，API 仍在变动。缓解手段是结构性的：`ctx.audio` 与其他服务无异，因此可以在其背后替换另一个引擎，而不触碰 `ctx.player` 或任何音效插件。这个抽象*本身就是*保险单。已作为最高优先级事项记录在风险登记册中（[10 §3](./10-roadmap.md#risk-register)）。

## 4. 术语表

以下术语在整套文档中始终按此处给出的精确含义使用。

| 术语 | 含义 |
|---|---|
| **内核（Kernel）** | `@BBeBee/kernel` —— Cordis 再加上 BBeBee 的引导启动、配置加载、插件解析与能力门禁。不是 Cordis 的概念。 |
| **Context**（`ctx`） | 一个 Cordis `Context`。同时是 DI 容器、事件总线与生命周期作用域。每个插件都会获得自己的派生上下文。 |
| **服务（Service）** | 在稳定的服务键（`ctx.fs`）上认领的一种能力。在 `@BBeBee/protocol` 中声明，在给定隔离作用域内任一时刻恰好由一个插件提供。 |
| **Fiber** | Cordis 中插件生命周期的单位。跟踪状态（`PENDING` → `LOADING` → `ACTIVE` → …），持有插件的可清理项（disposables），并在插件依赖变化时重新加载它。 |
| **Effect** | 通过 `ctx.effect()` 注册的一个可逆副作用。返回的 disposer 会在卸载时自动运行。 |
| **核心插件** | 实现某个平台服务的插件。位于 `packages/core-*`。是唯一允许导入平台 SDK 的代码。 |
| **功能插件** | 其余一切。只通过服务键触达平台。 |
| **提供方（Provider）** | 一个音源实现（`source-subsonic`）。一个*提供方插件*可以被实例化为多个*提供方实例*——两台 Navidrome 服务器就是同一个插件的两个实例。 |
| **URN** | `BBeBee:<providerInstance>:<kind>:<id>`。曲库实体的稳定标识符。 |
| **绑定（Binding）** | `media_bindings` 表中的一行，把某个曲目 URN 绑定到具体的本地文件。"这首曲目已下载"的实际含义即在于此。 |
| **链（Chain）** | 播放器的源节点与输出之间的一串有序 DSP 效果。 |
| **描述符（Descriptor）** | 一种与渲染器无关的 UI 贡献——一条路由、槽位填充、命令或设置页——由当前运行的外壳解析为真实组件。 |
| **外壳（Shell）** | 挂载 UI 的宿主应用：`apps/mobile` 或 `apps/desktop/renderer`。 |
